# 智能聚合路由使用说明

## 1. 能力边界

智能聚合路由只作用于 `api_model` 职员底座的单个 Agent Run 的每个 turn，支持：

- `fixed`：始终使用 Anchor；
- `smart_single`：按 `rules-v1`、能力门控、健康状态和确定性评分选择一个模型，并按错误策略重试/回退；
- `selective_ensemble`：仅在高复杂度、验证失败或低置信度等条件满足时执行 proposer + aggregator，proposer 禁止执行工具。

Codex CLI、Claude Code、OpenCode 仍由任务级公司/部门编排负责，不接受 Routing Policy，也不会被 turn 级路由改写。

## 2. 前置条件

1. Backend 已运行 migration `005_model_routing_metadata`，并发布包含模型路由元数据的签名 Catalog Release。
2. Desktop 已完成 SQLite migration `006_intelligent_routing` 和 `007_routing_capability_tags`，在设置页能够看到路由健康入口；顺序延迟任务的 dispatch spec 会同时固化任务能力标签。
3. Credential 已创建并 Probe 为 `ready`。Secret 只写入系统 Keychain；页面、日志、备份和路由查询都不会显示 Secret。
4. Credential 的新增、更新、Probe、删除使用客户端生成的幂等键；同一幂等键重复提交会复用 24 小时内的非敏感结果，改写请求内容会返回冲突。发布 API Model Profile 时会自动逐候选执行凭据 metadata 预检。
5. Profile 使用同一个固定 Catalog Release，所有智能候选均为该 Release 中的 Provider/Model Binding，且模型 `routing_enabled=true`。

## 3. 配置 API Model Profile

进入“职员模型底座”中的 API Model Profile，打开“配置路由”：

1. 选择模式和 Anchor；Candidate、Model Binding、Credential、eligible roles 和 fallback 顺序只能从已同步目录/ready Credential 中选择。
2. `fixed` 仍需保留 Anchor；智能模式至少保存两个合法 Candidate，Anchor 必须同时具备 `single` 与 `fallback` 角色。
3. 点击“校验并保存”。页面先调用 `routing.validatePolicy`，返回 issue 时按 JSON Pointer 显示并不会写入 Draft。
4. 已发布 Version 只读。要改变候选、Credential 或模式，先创建新 Draft，再重新校验和发布。

路由策略保存到 Profile Version；运行中的 Run 不会读取后续 Draft 或新 Catalog。新建 Run 时，策略、Candidate Deployment 和 Credential Secret Version 会固化到 Execution Snapshot v2。

## 4. 灰度阶段

Sidecar 启动时读取一次 `IBREEZE_ROUTING_STAGE`，默认 `observe`。修改变量后必须重启 Sidecar：

| 阶段 | 生产请求行为 |
|---|---|
| `observe` | 只执行 Anchor，同时记录规则建议，不增加 Provider 调用 |
| `shadow` | 生产请求仍不增加调用；只有内部脱敏 evaluation harness 可执行候选 |
| `smart_single` | 开启单模型选择和安全 fallback |
| `selective_ensemble` | 在规则触发且满足能力/容量/健康条件时开启 Ensemble |
| `learning_candidate` | 学习模型只记录建议，实际选择仍由 `rules-v1` 完成 |

阶段非法时按 `observe` 启动并记录安全错误。阶段不是公共 RPC，也不写入 Profile 数据。

## 5. 查看 Run 和手动覆盖

在任务详情打开“Run 路由观测”，可查看模式、Decision 数、实际模型、fallback hops、token usage、P50/P95 latency、Attempt 错误和 Outcome。详情不会显示 Prompt、候选正文、Credential Ref 原文或 Authorization。

Run 处于 queued/running 时可以设置后续 Turn Override：`force_fixed`、`force_single`、`force_ensemble` 或清除。Override 通过版本 CAS 写入，只影响尚未创建的 Decision，Run 结束后失效；不能绕过能力门控、Snapshot Lease、active bench 或 Ensemble 禁止条件。

## 6. 健康与故障处理

- 429、过载、传输暂态和超时按固定 retry 次数处理；每次物理请求都有独立 Attempt。
- `CONTEXT_OVERFLOW` 只允许更大 context；`AUTH_INVALID`/`INSUFFICIENT_CREDITS` 只允许更换 Credential/Provider；`BAD_REQUEST`/`POLICY_REFUSAL` 不重试。
- 连续失败会 bench Deployment；`AUTH_INVALID` 标记 `credential_invalid`，不提供 UI 绕过按钮。
- Credential 更新后必须重新 Probe；旧 Snapshot 使用固化的 Secret Version，不会静默切换。
- Snapshot 授权拒绝、hash 不一致或无法关联唯一 Attempt 时应停止 Run、保留审计证据并重新确认计划，不手工编辑 SQLite。
- `sequential_refinement` 的后续段在上游任务完成后会严格解析冻结的能力标签数组，并再次核对冻结的员工部门、Profile Version、Catalog Release、能力标签、TaskWorkspace 和 Workspace Grant；任一资源失效或冻结 spec 结构损坏时该段进入 `failed`，不会改用当前底座或全局目录资源。

## 7. 常用诊断入口

- `routing.getRunSummary`：Run 汇总；
- `routing.listDecisions` / `routing.getDecision`：turn、Attempt、错误、usage、Outcome；
- `routing.listDeploymentHealth`：当前公司候选健康；
- `routing.clearExpiredHealth`：仅清除已过期且 `availability_state=ready` 的记录。

所有时间在界面按北京时间（`Asia/Shanghai`）显示，数字最多保留两位小数且不补零。
