# iBreeze 部署文档

## 前置工具要求

| 工具 | 版本要求 | 用途 |
|---|---|---|
| Node.js | >= 20 | 前端构建与 lint |
| npm | >= 10 | Node 包管理 |
| Python | >= 3.12 | Backend API / Sidecar |
| uv | >= 0.4 | Python 包管理 |
| Rust | >= 1.75 | Desktop Core |
| cargo-nextest | 最新 | Rust 测试运行器 |
| cargo-llvm-cov | 最新 | Rust 覆盖率 |
| Playwright | 最新 | E2E 测试 |

缺失任一必需工具时 `scripts/verify-all.sh` 直接失败。所有门禁（lint、typecheck、test、coverage、E2E、security audit）失败时总脚本返回非零退出码。

验证内容：
- packages/contracts lint：JSON Schema + Registry 合法性
- Rust desktop-core：fmt、clippy、test (cargo-nextest)、coverage (cargo-llvm-cov, 阈值 100%)、`cargo audit`
- Python backend-api：ruff lint、mypy typecheck、pytest coverage (阈值 100%)
- Python sidecar：ruff lint、mypy typecheck、pytest coverage (阈值 100%)、`pip-audit`
- TypeScript desktop：lint、typecheck、test
- TypeScript admin-web：lint、typecheck、test
- 契约漂移检查：`scripts/check-contract-drift.sh`
- E2E 测试：Playwright
- 安全门禁：Trivy 容器扫描、`cargo deny` license/adv 检查

所有覆盖率阈值固定为 100%，不允许低于此阈值的提交。

## 系统架构

### 远程服务端

| 服务 | 用途 | 端口 |
|---|---|---|---|
| postgres:16 | 数据库 | 51543 |
| minio/minio | S3 对象存储 | 51900 (API) / 51901 (Console) |
| backend-api | FastAPI 后端 | 51080 |
| admin-web | React 管理后台 (Vite) | 51421 (dev) |
| nginx:alpine | API 反向代理 | 51080 → backend-api |

### Desktop 本地组件

| 组件 | 策略 | 说明 |
|---|---|---|
| Rust Trusted Host Kernel | 不可旁路的可信基座 | Duplex UDS Multiplexer、Credential HTTP Broker、CONNECT Egress Proxy、Process Supervisor/Seatbelt |
| Python Sidecar Kernel | 业务域核心 | 11 阶段启动/9 步关闭、Profile 持久化 Kernel（Migrator + WriteQueue + UoW + ReadPool）、Worker Supervisor、Review/Completion State Machine |
| Rust ProcessSupervisor | Agent 进程边界 | 固定 Execution Snapshot（真实可执行路径、策略哈希、截止时间、Agent 类型）、独立进程组、argv/workspace 校验、Catalog adapter contract/平台/版本范围与 `probe_argv` 校验、每进程 egress lease、超时 SIGINT→SIGTERM→SIGKILL、stdout/stderr 摘要；单行输出上限 4 MiB、单流总量上限 16 MiB，超限 fail-closed；status 区分 `cancelled`/`timed_out`；macOS 使用 Seatbelt。签名 Catalog 的每个版本范围必须包含 `supported_platforms` |
| Credential HTTP Broker + Egress | API Model 网络边界 | Keychain 凭据只在 Rust 内存中展开；每个 Run 创建域名白名单 CONNECT lease，HTTP 结果通过同一认证 IPC Session 的 `credential.http.event` 反向通知返回 Sidecar；API Model 的模型、Provider、Credential、Workspace 和只读 ToolPolicy 必须来自 Execution Snapshot，取消调用 `credential.http.cancel` |
| UDS IPC | 认证帧协议 | 4B 长度前缀 + framed JSON-RPC 2.0；握手后的正向和反向调用复用同一个 IPC Session，禁止 Sidecar 自连自身 socket |

Review 与 Workspace 的执行边界：Review 状态机的 `StartReview`、`StartIssueFix`、`VerifyIssue`、`CloseIssue`、`RejectIssue` 仅通过 Sidecar 内部 Command Bus 调用，并在 Outbox 当前 WriteQueue 事务中完成；`review.resolveIssue` 必须提交 resolution artifact hash、修复 Run、复测 Artifact、摘要和 expected version。Workspace Git 仅允许固定 argv、数据库绑定 cwd 的受控执行器；`workspace.apply` 会在合并前检查用户工作树 clean、当前分支和确认时 baseline，`workspace.cleanupTask` 不得使用强制删除。

## 运行时调度与执行

### 计划确认与分发（ConfirmPlan）

`task.confirmPlan` 是唯一的计划确认入口，由 `ibreeze/orchestration/confirm_plan.py` 的
`ConfirmPlanCommand` 在同一 WriteQueue 事务中完成校验、快照、任务创建和运行入队。请求必须携带
`company_id/company_task_id/plan_artifact_id/plan_sha256/expected_version`，可选的
`workspace_grant_ids` 只用于绑定已授权工作区；不存在已验证的 active Catalog Release 时返回
`waiting_resource`，绝不会自动创建本地或未签名 Catalog。

事务内固定执行以下步骤：

1. 校验当前 CompanyTask 为 `awaiting_user_confirmation`、PlanVersion 为当前 awaiting 版本、内容哈希和乐观锁版本一致。
2. 校验 Company/Department revision、TaskWorkspace、Catalog Release 和职员运行配置，并创建不可变 AvailabilitySnapshot、ExecutionSnapshot。
3. 创建 DepartmentTask、依赖、EmployeeTask、AgentRun 和 `runtime_queue` 项；所有 Run 均绑定快照 hash，不能由前端或模型传入替代工作区路径。
4. 写入 `company_task.status_changed` 事件和 Outbox；状态沿 `approved → dispatching → checking_resources → executing` 完整记录，任一步失败整体回滚。

所有生产代码都必须通过 `task.confirmPlan` 创建任务或 Run，不得绕过该入口直接写入任务编排数据。

低层 `runtime.run` 仅用于已经完成快照的内部执行请求。请求必须同时携带
`company_id`、`agent_id`、`company_task_id`、`conversation_id`、
`availability_snapshot_id`、`execution_snapshot_id`、`model_id`、`run_purpose` 和
`adapter_type`；服务端会再次校验快照归属、过期时间、职员状态、会话状态和任务关联，成功后写入
`run.queued` 的 RunEvent、DomainEvent、Outbox 和 RuntimeQueue。前端不能只传任务 ID 触发执行。
生产 RPC 最终委托 `ibreeze.runtime.gateway.start` 这一唯一 Run 创建实现；除计划确认和该 Gateway
外的模块不得直接插入 `agent_runs`，且请求中的模型/适配器必须与 ExecutionSnapshot 的不可变绑定一致。

Review Issue 的状态迁移也必须通过内部 Command Bus 和同一 WriteQueue 事务完成：迁移到
`verified` 时必须提供同公司且仍为 `active` 的 `verifier_employee_id`；迁移到
`rejected` 时必须提供 1–2000 个字符的 `rejection_reason`，`blocker/high` 问题不能被驳回。

Rust 进程输出的 stdout/stderr 由共享发送锁保护，序号分配和 IPC 通知在同一临界区内完成；版本探测的失败和超时路径会等待输出读取任务退出。反向
`credential.http.start` 的 `deadline_at` 必须是当前时间起 1–600 秒内的 RFC3339 时间，非法或过期值直接返回 `PROVIDER_DEADLINE_INVALID`，不会回退为默认超时。

公共 RPC 的 `meta` 按同一 Registry 严格校验：写方法必须携带 UUID `idempotency_key`，读方法不得携带；未知字段、无时区时间或已过期 `deadline_at` 均返回 `VALIDATION_FAILED`（已过期时间返回 `IPC_DEADLINE_EXCEEDED`）。

### 运行执行器（Run Executor）

`ibreeze/runtime/run_executor.py` 负责处理排队中的 Run，生产入口是 `RuntimeWorker`：

- 在同一个 WriteQueue 事务中按公司公平性、优先级和 FIFO 领取 Run，创建 300 秒 lease；只领取带 `run_id` 的执行项
- 在独立的短 WriteQueue 事务中推进 `queued → probing → starting → running`，启动前通过内部 `StartEmployeeTask` Command 将员工任务从 `assigned/ready` 原子转为 `running`
- 执行阶段不持有 SQLite 写事务：CLI 只构建 argv 并调用 Rust ProcessSupervisor，API Model 只通过已认证 Rust Credential HTTP Broker 运行完整 Agent Loop
- 每 30 秒通过 WriteQueue 续租；结束、取消、异常和 Worker 停止都会先清理 Rust 进程/lease，再原子释放 `runtime_queue`
- 完成时在同一事务写入 `agent_run_events`、`domain_events` 和 Outbox；`run.completed` 只触发 `EvaluateEmployeeSubmission`，不会直接把业务 Task 标记为完成
- `run.cancel` 通过 Rust `runtime.process.cancel` 终止进程组后再写入 `run.cancelled`；`run.resume` 重新校验并创建新的队列项，最多 6 次尝试
- CLI 输出超过单行 4 MiB 或单流 16 MiB 时 Rust 立即终止进程组并返回 `RUNTIME_OUTPUT_LIMIT_EXCEEDED`；正常取消与 deadline 超时分别返回 `status=cancelled` 和 `status=timed_out`，RuntimeWorker 映射为对应终态，不把用户取消误报为失败

### 验证循环（Verification Loop）

`ibreeze/runtime/verification_loop.py` 在 Run 执行完毕后运行验证检查：

- 自动运行验证工作流，确认产出符合预期
- 若验证失败，最多执行 **5 轮修复循环**（fix cycles），每轮重新提交修复并再次验证
- 超过修复上限后将 Run 标记为 `failed` 并停止重试

### 相关运行时模块

| 模块 | 职责 |
|---|---|
| `runtime/scheduler.py` | 公平调度、优先级排序、租约管理 |
| `runtime/run_executor.py` | Run 执行入口；只构建 argv，不创建子进程 |
| `runtime/process_supervisor.py` | Rust `runtime.process.*` 反向 RPC facade；仅组装固定请求并消费 `registered/output/exited` 通知，不创建子进程 |
| `runtime/transport.py` | API Model 通过已认证 Session 调用 `credential.http.start` / `credential.probe` |
| `runtime/model_tools.py` | API Model 固定只读 `read_file`、`list_files`、`search_text` 工具；所有路径拒绝 symlink、`..` 和 Workspace 外访问 |
| `runtime/verification_loop.py` | 验证 + 修复循环 |
| `runtime/checkpoint.py` | 执行快照与断点续跑 |
| `runtime/event_compactor.py` | 事件压缩与日志裁剪 |
| `orchestration/confirm_plan.py` | 计划哈希确认、资源快照、Task/Run 原子分发 |
| `persistence/write_queue.py` | 写入序列化与备份屏障（`barrier()`） |

### 外部写入审批边界

外部写入必须同时携带人工 `approval_id` 和 Rust `workspace_grant_id`。审批 `target_json` 固定包含 `target_realpath`、`operation`、`expected_old_sha256`、`source_sha256`、`workspace_grant_id`，并保存 canonical JSON 的 `target_sha256`；F.4 请求另外携带 `run_id`、staging 相对路径、source size 和 `expires_at`。create/replace 的 source 只能来自 `${IBREEZE_PROFILE_ROOT}/external-write-staging/{approval_id}/`，必须校验 SHA-256、大小、0600 权限和无 symlink；delete/create_directory 不得携带 source。Rust 只执行单目标原子动作并返回 receipt，Sidecar 逐字段校验 receipt 后才消费审批。

### 备份与恢复

备份系统使用 **SQLite Online Backup API** 在 WriteQueue 屏障后创建一致性快照，输出为 `tar.zst` 压缩包：

- **命令**：RPC `backup.create` / `backup.restore`
- **格式**：`{backup_id}/backup.tar.zst`（含 `data/profile.db` + CAS 对象 + `manifest.json`）
- **敏感文件排除**：`secrets.json`, `.env`, `credentials.json`, `keys.db`, `id_rsa`, `id_ed25519`
- **外部引用冻结**：备份时自动收集带 FK 约束表的所有行，存入 manifest 的 `external_refs` 字段
- **恢复验证**：还原时执行 `integrity_check`、migration 链完整性、FK 引用完整性
- **保留策略**：支持每日保留（默认 7 天）和每周保留（默认 4 周）
- **一致性保证**：WriteQueue `barrier()` 确保所有待处理写入完成后再进行快照

应用关闭必须先停止 Workers，再等待 WriteQueue drain/barrier 完成，最后关闭数据库连接和 IPC；禁止在队列仍有写入时关闭数据库。

### 知识库

`ibreeze/knowledge/` 模块管理知识导入、嵌入、检索：

- **SQLite 存储**：`knowledge_items` 表存元数据，`knowledge_fts` 表支持全文检索
- **LanceDB 向量索引**：`knowledge_embeddings` 表，384 维嵌入向量，支持按 `company_id` / `generation_id` 过滤
- **代际追踪**：`embedding_generations` 表记录 `model_key`、`vector_dimension`、`source_event_sequence`
- **一致性检查**：`check_consolidation()` 对比 SQLite 与 LanceDB 计数，暴露代际详情
- **ACL 过滤**：检索前通过 `permitted_knowledge_ids()` 按 `visibility`（company/department/task/private）预授权

## 常见运维

### 查看日志

```bash
docker compose -f deploy/docker-compose.yml logs -f backend-api   # 仅后端
docker compose -f deploy/docker-compose.yml logs -f postgres      # 仅数据库
docker compose -f deploy/docker-compose.yml logs -f minio         # 仅对象存储
```

### 桌面客户端日志

桌面客户端 Rust Core 使用 `tracing` 输出日志：

- **控制台**：stderr 实时输出（开发模式）
- **文件**：`$LOCAL_APP_DATA/ibreeze/logs/desktop-core-{YYYY-MM-DD}.log`（每日轮转，保留 30 天）
- **格式**：JSON（文件）/ ANSI 彩色（控制台）
- **级别**：默认 `info`，可通过环境变量 `RUST_LOG` 覆盖

```bash
# 查看最新日志文件
ls ~/Library/Application\ Support/ibreeze/logs/  # macOS
cat ~/Library/Application\ Support/ibreeze/logs/desktop-core-$(date +%Y-%m-%d).log

# 调整日志级别（开发调试）
RUST_LOG=debug cargo tauri dev
```

### 停止/重启

```bash
docker compose down        # 停止所有服务
docker compose up -d       # 重新启动
docker compose restart     # 重启
```

### 完全重置（清除数据）

```bash
docker compose down -v     # 停止并删除卷（数据会丢失）
docker compose up -d       # 重新创建
# 之后重新创建 MinIO 存储桶和运行迁移
```

### 从零重新部署

```bash
# 卸载旧版
docker compose down -v
docker system prune -a --volumes -f

# 清理本地缓存
rm -rf apps/backend-api/.venv sidecar/.venv apps/admin-web/node_modules apps/desktop/node_modules
pip cache purge
uv cache clean
npm cache clean --force

# 重新安装
cd apps/backend-api && uv sync
cd ../admin-web && npm install

# 构建 Docker 镜像
cd ../..
docker compose build
docker compose up -d
# 然后创建存储桶 + 迁移数据库
```
